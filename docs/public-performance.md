# 公開ページの性能計測

トップと記事ページを分け、モバイル・PCそれぞれを3回ずつ測る。
Lighthouseのバージョン、Chrome、マシン負荷を揃え、中央値と各回のばらつきを比較する。
開発サーバーではなく本番ビルドを使用する。

```sh
mise exec -- node scripts/benchmark-public-pages.mjs \
  'https://weblog.ason.as/' \
  'https://weblog.ason.as/RubyKaigi%202026%20follow%20up%E3%81%A7%E7%99%BB%E5%A3%87%E3%81%97%E3%81%A6%E3%81%8D%E3%81%9F' \
  /tmp/weblog-lighthouse
```

Chromeが必要。CLIはLighthouse 13.4.0を使用する。
HTML・JSONレポートと、各回の指標を記録した `measurements.json` を出力する。
モバイルはLighthouseの標準設定、PCは `--preset=desktop`。
認証済みのブラウザプロファイルは使わない。

## 2026-09-09の基準値

Chrome 152.0.0.0、Lighthouse 13.4.0で本番URLを測定した中央値。
PageSpeed Insightsとは実行場所・Chromeバージョンが異なり、絶対値は直接比較しない。

| 対象 | スコア | LCP | CLS |
| --- | ---: | ---: | ---: |
| トップ・モバイル | 73 | 6.23秒 | 0 |
| トップ・PC | 90 | 1.12秒 | 0.182 |
| 記事・モバイル | 82 | 4.83秒 | 0 |
| 記事・PC | 99 | 0.91秒 | 0 |

トップのモバイルはスコア55〜73、CLS 0〜0.609と変動が大きい。
中央値だけでは遅れて届くコンテンツによるずれを見落とす。
記事は専用の公開用JSを使用しており、トップと同じ修正対象にはしない。

## トップの比較条件

変更前はmainの770a660、変更後は性能改善の作業ブランチ。
両方をViteの本番モードでビルドし、同じ公開APIレスポンスと画像をローカルに固定した。
APIは200ms、タグAPIは500msの応答遅延を設定。圧縮・キャッシュ条件も共通。
この比較はクライアント側の変更による効果を確認するもので、AWS・CDN・cold startの改善を示すものではない。
本番への適用後には本番URLで改めて計測する。

各3回の中央値。転送量は画像だけでなくページ全体を含む。

| 指標 | モバイル・変更前 | モバイル・変更後 | PC・変更前 | PC・変更後 |
| --- | ---: | ---: | ---: | ---: |
| スコア | 58 | 88 | 89 | 97 |
| LCP | 6.63秒 | 3.31秒 | 1.19秒 | 1.19秒 |
| CLS | 0.324 | 0.086 | 0.182 | 0.043 |
| 転送量 | 1.76MB | 0.45MB | 14.40MB | 1.15MB |

スマートフォンのタグ配置・スケルトン追加前の測定値。
修正後のスコアは3回ともモバイル88・PC97。
画像生成のローカル検証にはlibvips 8.18.6を使用した。
未解消の主な待ち時間はトップの初期データ取得とJSの読み込み。
トップのHTML先行生成、記事のカバー画像の縮小版利用はこの変更には含まない。

## 実装と運用

- ヘッダーの初期レイアウトをHTML読み込み時から決め、読み込み文言のマージンの相殺がbody全体を動かさないようにする。
- タグは文字量に応じたピル幅を保つ。PCは自然に折り返し、モバイルは2段それぞれを独立した行として横スクロールする。モバイルのタグは1行表示で高さ44pxとし、上下のタグで列幅を共有しない。
- タグ取得中はスケルトンを表示する。モバイルは読み込み前後で129pxの領域を確保し、取得失敗や空の結果でも領域を保つ。動きを減らす設定ではシマーを停止する。PCは最低限の高さを確保するが、折り返し行数による高さの変化は残る。
- タイムライン待機中は高さを確保し、フッターの早すぎる読み込みを避ける。スケルトンはタグの取得中を対象とし、初期HTMLへのタグの埋め込みは含まない。
- カードは640px幅のWebPを遅延読み込みする。ヒーローは `<picture>` を使い、600px以下の画面では640px・1280pxの候補を `srcset` と `sizes` で選択する。広い画面では元画像を使い、高解像度の表示を維持する。ヒーローの取得優先度は高くする。
- 公開処理で縮小版を生成し、S3に保存する。閲覧時の画像変換は行わない。生成済みの画像と元画像は上書きしない。
- 縮小版がまだない場合、ブラウザは元画像へ戻す。

実画像でのファイルサイズ例：12,799,044 bytesのPNGは640pxで30,348 bytes、1280pxで82,244 bytes。
メイン画像の771,850 bytesのWebPは、それぞれ34,564 bytes、106,366 bytesになった。

既存記事のカバーにはバックフィルが必要。`--apply` なしでは公開記事の対象画像一覧だけを表示する。
認証済みのAWS環境から実行し、元画像のGetObjectと縮小版のPutObject権限を使う。

```sh
mise exec -- ruby bin/backfill-cover-variants --host DSQL_HOST --site-bucket SITE_BUCKET
mise exec -- ruby bin/backfill-cover-variants --host DSQL_HOST --site-bucket SITE_BUCKET --apply
```

Rubyの画像処理にはlibvipsが必要。Lambdaイメージには既に含まれる。
ローカルではHomebrewの `vips`、UbuntuのCIでは `libvips-tools` を使う。
デプロイ時は既存画像の縮小版を先に用意し、フロントエンドと公開処理の更新後に本番計測を行う。
この記事の本文HTML再生成は、トップの画像切り替えには不要。

S3のHeadObjectは、ListBucket権限がない場合に未生成キーへ403を返す。
縮小版の存在確認ではこれを考慮し、取得・保存自体の権限エラーは隠さない。
[AWS HeadObjectの仕様](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html)
