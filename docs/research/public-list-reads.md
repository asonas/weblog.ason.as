# 公開一覧の限定読み取り

Issue [#186](https://github.com/asonas/weblog.ason.as/issues/186) の比較。2026-09-27 JST。

`limit` のある公開一覧では、まず公開headと有効版から版ID、並び順、公開/更新時刻だけで対象を確定し、選んだ版の本文とAtom情報を取得する。`limit` のない一覧処理は変更しない。日記種別の判定とタイムラインの日付キーは今も本文を参照するため、候補の全本文をDBが読まなくなると断定しない。スキーマとインデックスは変更していない。

## 同一人工データでの応答比較

`mise exec -- ruby -Ilib scripts/measure-public-list-reads.rb` で再現できる。SQLiteに公開済み人工記事1,000件を用意し、旧SQLと新SQLに対して通常・日記・記事・タイムライン・空の月のAPI応答、存在するページの次ページを比較した。計9個のAPIウィンドウ（SHA-256 `3eff6b20b8b539e27c3be2ba406e5ccbcde3d648cf61a24c31b914a11e1cf4c7`）、Storeの31件一覧と13件タイムラインの全行が一致した。取得本文のバイト数も同じで、アプリへ返るデータ量の削減ではない。

| ローカルSQLite、各5回の中央値 | 旧SQL | 新SQL | 返却行数 / 本文バイト数 |
| --- | ---: | ---: | ---: |
| 一覧 | 1.267ms | 0.928ms | 31 / 37,572 |
| タイムライン | 2.805ms | 2.656ms | 13 / 15,756 |

SQLiteの実行計画では旧SQLがhead走査後にAtom情報を結合して並べ替え、新SQLは対象IDを決めてから公開版とAtom情報を結合する。これだけでDSQLの処理量や請求額は推定しない。

## DSQL実行計画

本番DSQLの公開済みデータを変更せず、`EXPLAIN ANALYZE VERBOSE` を旧・新の通常一覧31件、タイムライン13件、日記一覧31件に各1回、合計6回実行した。加えて新SQLの前後カーソル、記事種別、月フィルターのパラメータ付き読み取りを3回確認した。接続確認の`SELECT 1`を含め、成功したDSQL読み取りは10回、書き込みは0回。既存の公開headは851行、公開版主キー走査は862行だった。実行計画は対象選択、本文取得、Atom結合を含む**SQL全体**の値。新SQLのAtom結合は通常851→31回、タイムライン851→13回、日記509→31回になった。

取得した6件の実行計画は[JSON](public-list-reads-dsql-plans.json)に保存した。SQL文は比較用の読み取り専用文で、問い合わせ結果の本文はこの記録に含めていない。

| SQL全体の単発実行 | 旧: 実行時間 / Read DPU / Total DPU | 新: 実行時間 / Read DPU / Total DPU |
| --- | ---: | ---: |
| 通常一覧 | 316.643ms / 4.06018 / 4.52489 | 31.040ms / 2.72854 / 2.76035 |
| タイムライン | 324.129ms / 2.86781 / 3.22270 | 21.889ms / 2.64491 / 2.66775 |
| 日記一覧 | 191.935ms / 2.69365 / 2.88646 | 34.094ms / 2.71718 / 2.75215 |

日記一覧のRead DPUはわずかに増えた。3種類ともTotal DPUは下がったが、1回ずつの観測であり、実トラフィックの平均、月額費用、p95の根拠にはしない。実行計画のStatement DPUは請求値ではなく、トランザクション最小値やバックグラウンド作業を含むCloudWatch集計とも一致しない。[AWSのDPU解説](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/understanding-dpus-explain-analyze.html)を参照。今回取得したのはSQL実行計画であり、本番HTTP応答や利用者の表示速度は未計測。
