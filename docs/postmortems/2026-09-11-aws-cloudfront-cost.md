# 記事の一括再生成に伴うCloudFront invalidation料金の増加

作成日: 2026-09-11 / 状態: ドラフト・対応途中

対象はWeblog.ason.asのAWS運用で発生した、想定外のCloudFront invalidation料金である。
金額と対応状況は2026年9月11日の調査時点の記録に基づく。
時刻は明記したものを除き日本時間（JST）とする。

## Summary / 概要

2026年9月9日から10日にかけて、記事表示の修正を既存の公開ページへ反映するため、複数回の一括再生成を行った。
再生成には通常の公開処理を使用し、各記事とリンク先のwikiハブに対するCloudFront invalidationが実行された。
この結果、9月10日（UTC）の課金対象は無料枠を除いて5,999パスとなり、invalidationだけで29.995ドルが発生した。

変更する記事の範囲や公開内容は事前に確認した一方、再生成から派生するinvalidationのパス数と料金を見積もらずに実行した。
さらに、実装は更新されなかった既存のwikiハブも無効化対象へ含めており、必要以上にパス数を増やす構造だった。

利用者に届いたメール通知をきっかけに、9月11日にAWS料金の調査を行い、費用増加の内訳が判明した。
デプロイ時のinvalidationを廃止してTTLに任せる方針は決定したが、その変更は本番未反映である。
記事公開処理のinvalidationは残っており、一括再生成による費用増加への恒久対応は完了していない。

## Impact / 影響

9月11日15:42のCost Explorer取得値は次のとおりだった。
集計期間は9月1日から9月11日まで（終了境界は9月12日）で、AWS上では推定値である。

| 項目 | 金額・使用量 |
| --- | ---: |
| AWS全体の月初来料金（税込） | 37.4927174049ドル（約37.49ドル） |
| 設定されていた月額予算 | 20ドル |
| CloudFront全体 | 29.995950598ドル |
| うちinvalidation | 29.995ドル |
| 税 | 3.41ドル |
| invalidationと税を除いた月初来料金 | 約4.09ドル |

約4.09ドルは調査時点までの累計であり、今後の月額料金の予測ではない。
約30ドルも毎回のデプロイ料金ではなく、今回の大量の無効化により発生した月初来の料金である。
通常のデプロイは5パスであり、無料枠消費後の単純計算では1回0.025ドルとなる。

本件による閲覧停止やデータ消失の報告は確認していない。
ただし、全期間の可用性を検証したわけではなく、サービス影響が皆無だったと断定はしない。
利用者には、想定外の支出に加え、料金調査と運用方針の見直しが必要になった。

関連する費用調査の結果、利用者の承認を受けてCloudWatchアラーム27個を削除した。
これによりアラームによる障害の自動検知・通知が失われたことは、対応に伴う運用上の影響である。
ログ、メトリクス、ダッシュボードは維持した。

## Root Cause / 根本原因

### 運用上の原因

一括再生成の承認判断に、対象ページ数と表示内容だけでなく、従量課金される後続処理の見積もりを含める必要があった。
実際には、実行を担当したエージェントがinvalidationの発生パス数、月間無料枠の残量、見込料金を提示しなかった。
利用者が承認した作業範囲と、その作業が引き起こす費用への認識に差が生まれた。

### 実装上の原因

`WebmentionSitePublisher` は記事の公開時に、記事ルート、旧ルート、リンク先のwikiハブをまとめて無効化する。
多数の記事を再生成すると、記事数だけでなく各記事のリンク先に応じて無効化パス数が増える。

`publish_linked_hubs` は既存ハブへの書き込みを条件付きPUTで回避するが、戻り値には既存ハブを含むすべての対象名を返す。
その戻り値を無効化対象に使うため、内容が更新されていないハブにもinvalidationが発生する。
同一リクエスト内の重複除去はあっても、別の記事処理との間で共通ハブをまとめる仕組みはない。
この実装による増加分を金額として切り分ける調査は未完了である。

一括再生成では、個々の公開処理のinvalidationを抑止し、全件の反映後に`/*`を1回だけ送る選択肢もあった。
ワイルドカードは対象ファイル数にかかわらず1パスとして課金されるため、この方法なら当該一括処理由来のinvalidationは1パスで済み、今回の約30ドルの主要因を回避できたと考えられる。
複数の個別パスを一つのAPIリクエストへ詰めるだけでは、課金パス数は減らない。
また、記事ごとに`/*`を送ればその回数分が計上されるため、最後にまとめて実行することが重要である。
この選択肢を事前検討しなかったことも、費用設計上の不足だった。
出典: [AWSのワイルドカード課金説明](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/PayingForInvalidation.html)。

### 判断を難しくした要因

コードのデプロイと既存記事の一括再生成は別の操作だが、会話の中では「デプロイに伴う料金」として捉えやすかった。
通常デプロイの5パスと、一括再生成による大量のパスを区別した説明が後手に回った。
また、Cost Explorerや無料枠の表示は即時ではないため、実行直後の表示だけでは費用増加を判断できなかった。

## Trigger / 直接のきっかけ

表示修正を過去の記事へ反映するために、短期間に複数回、ほぼ全公開ページの再生成を実行したことが直接のきっかけだった。
通常の公開処理に組み込まれたinvalidationも同時に大量実行され、月間無料枠を超えた。

料金データ上、9月9日（UTC）までに986パスを使用しており、無料枠1,000パスの残りは14パスだった。
9月10日（UTC）の6,013パスから残り14パスを引いた5,999パスが課金対象となった。

`5,999パス × 0.005ドル = 29.995ドル`

無料枠はリクエスト数ではなく無効化するパス数で数えられる。
同じURLでも別のリクエストで無効化すれば再び数えられる。
料金体系は[AWSのinvalidation課金説明](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/PayingForInvalidation.html)と[単価の公式案内](https://aws.amazon.com/about-aws/whats-new/2015/05/amazon-cloudfront-makes-it-easier-to-invalidate-multiple-objects/)による。

## Detection / 検知

利用者にメール通知が届き、料金が気になって「今のAWSのコストがいくらなのか」と調査を依頼した。
これを受けてCost Explorerを確認し、CloudFront invalidationが費用増加の主因だと特定した。
メールが検知のきっかけだったことは利用者本人の確認による。
通知の種類、受信時刻、本文、しきい値は未確認であり、AWS Budgetsや無料枠通知のどちらだったかは断定しない。

検知時には実績約37.49ドルに対して月間予測約10.44ドルという不整合もあり、予測値を安全判断に使えなかった。
この不整合の原因自体は確定していない。
AWSはCost Explorerを少なくとも24時間ごとに更新する一方、反映がさらに遅れる場合もあると説明しているため、実行前の見積もりが必要だった。
出典: [Cost Explorerの更新頻度](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-what-is.html)。

## Response / 対応

1. サービス別・日別・使用タイプ別の料金を取得し、約30ドルがinvalidation由来であることを確認した。
2. CloudFront履歴と公開処理を調べ、記事の一括再生成とハブの無効化が大量実行につながる構造を確認した。
3. 本番の固定5ファイルについて、レスポンスの`Cache-Control: public, max-age=0, must-revalidate`とCloudFrontの最小TTL 1秒を確認した。
4. 利用者の選択に従い、デプロイ時のinvalidationステップを削除した。関連テストは10件・148 assertionsが成功し、RuboCopと差分検査も成功した。
5. 関連する無料枠調査としてCloudWatchとSQSを確認した。

固定5ファイルは現在の設定では実質1秒のキャッシュ寿命になるため、デプロイ時の明示的な無効化をやめてTTLに任せる方針とした。
TTL経過は全拠点への即時配信ではなく、通常は次のアクセス時の再検証につながる。
ハッシュ付きアセットには別途1年間のキャッシュ設定があるため、CloudFront全体のTTLが1秒という意味ではない。
出典: [CloudFrontの有効期限と再検証](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html)。

対応の反映状況は次のとおりである。

| 対応 | 状態 |
| --- | --- |
| デプロイ時のinvalidation廃止 | ローカル実装・検証済み。コミット、main統合、push、本番での動作確認は未実施。 |
| 記事公開・一括再生成のinvalidation削減 | 未実施。従来の処理が残っている。 |
| CloudWatchアラーム27個の削除 | 承認を受け本番apply済み。残数0、後続plan差分なし。main統合済み、push未実施。 |
| SQSのポーリング変更 | 調査のみ。設定変更なし。 |

CloudWatchの無料枠表示8.7582174 / 10は発報回数ではなく、利用時間で按分されたアラーム使用量だった。
当月の無料枠を優先するという利用者の判断で全27個を削除したが、未反映の使用量があるため、当月の無料枠内への収束を保証したものではない。

SQSの約31万Requestsも、滞留メッセージ数ではない。
3つのLambdaイベントソースによる常時ポーリングを確認し、9月1〜10日（UTC）のメトリクスでは空受信が277,503回、送信が8,922件だった。
課金集計と期間・集計方法が異なるため、これらから請求リクエスト数の厳密な割合は算出しない。
調査時のSQS料金は0ドル、月間予測は約84.7万Requestsであり、本件の約30ドルの原因ではなかった。

## What went well / うまくいったこと

- 既存記事の一括更新では、対象の事前抽出と利用者の承認、試験的な反映、公開成果物の確認を行っていた。変更対象の把握には役立った。
- 費用増加を検知した後は、総額だけでなく使用タイプと日別の数値を確認し、29.995ドルの計算根拠まで説明できた。
- メール通知が利用者の確認行動につながり、費用の内訳を調査するきっかけとして機能した。
- CloudWatchの削除では、利用者に通知喪失を説明したうえで、保存したTerraform planをapplyし、実リソースと後続planを確認した。
- 調査の結果、SQSに対しては費用削減を目的とする追加の構成変更を行わず、現在の無料枠内で経過を見る判断ができた。

## What went wrong / うまくいかなかったこと

- 対象記事の承認を得る際、後続の従量課金まで見積もらなかった。費用面で必要な判断材料をエージェントが提示できていなかった。
- 一括再生成に通常公開の無効化処理をそのまま使い、変更のないハブも対象に含めた。
- 一括処理の最後に`/*`を1回だけ送る方法を検討せず、個別パスを繰り返し無効化した。
- 短期間の複数回の一括再生成について、累積パス数と残り無料枠を確認する判断点がなかった。
- 初期の説明では「全体として安く運用できている」という評価が先行し、確認済みの累計額と今後も費用が発生する条件を十分に分けていなかった。
- 通常デプロイのinvalidationを廃止するだけでは、今回の主因である記事再生成の経路は解消しない。方針決定、コード変更、本番反映を区別した進捗管理も必要である。

## Where we got lucky / ラッキーだったこと

- 利用者がメール通知を見て調査を依頼したため、さらに一括作業を重ねる前に料金の内訳を確認できた。
- 調査時点では想定外の費用の大部分を一つの使用タイプに絞れ、29.995ドルの根拠を再現できた。ただし、月額予算20ドルはすでに超えていた。
- SQSはリクエストが多く見えても無料枠内で、調査時点では追加料金を生んでいなかった。
- 固定5ファイルの実際のキャッシュ寿命が短く、デプロイ時のinvalidation廃止については、大規模なアセット構成変更をせずに進められた。
