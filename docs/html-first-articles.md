# 公開記事のHTML配信

Issue #140。公開記事は公開処理で本文とhead情報を生成してS3へ保存し、CloudFrontから返す。閲覧用JSは本文を再構築せず、メディアの待機状態、埋め込み、検索とユニバースを追加する。編集・ホーム・検索ページは既存のアプリを使う。

## 配信物と閲覧の境界

- `static/authoring/public.html` は公開処理が読むテンプレート。記事ごとの本文・title・description・canonical・OGPは公開処理で挿入する。記事名と衝突しない静的アセットの名前空間に置く。
- 閲覧用JS・CSSはハッシュ付きの静的アセット。公開記事の初期表示は記事API、認証API、エディタに依存しない。
- `/editor/:id` と `/search`、`/authoring/webmentions` はCloudFront Functionが既存の `index.html` へ書き換える。
- その他の存在しない公開オブジェクトは `static/authoring/404.html` をHTTP 404で返す。存在しない記事をSPAの空シェルへ戻さない。
- 記事レイアウトは既存の閲覧画面と共通のCSSを使う。本文はサーバー生成HTMLのまま維持し、検索とユニバースだけを独立してマウントする。ユニバースは画面から600px以内に近づいたときに既存の関連ページAPIを呼び、続きを読み込む操作とノードの詳細表示に既存部品を使う。
- 画像の寸法が記法に含まれる場合はwidth/heightを出力する。寸法がない画像は元画像の縦横比で表示し、一律16:9には押し込めない。この場合の読み込み時の高さ確保は未解決。動画は記法にある寸法を使い、なければ16:9。既存の動画には独立したポスターURLがないため、最初のフレームを読む既存の `#t=0.001` を維持する。
- シマーは本文には適用しない。動画・画像・埋め込みの完了かエラーで終了し、画面に近づいてから15秒経過しても応答がなければ終了する。後から読み込みが完了した場合もコンテンツは表示できる。JS無効時はシマーを表示せず、動きを減らす設定ではアニメーションしない。
- Speaker Deckのメタデータ取得は画面付近まで遅延する。外部プレイヤーの取得に失敗しても本文と元リンクは残す。

## 本番移行の順序

コードの配備だけでは既存記事は変わらない。アプリケーションの配備、記事の再生成、CloudFrontの404切替を別々に確認する。本番操作は承認されたデプロイ時に行う。

1. 通常のValidate/Deployワークフローでビルド済みの閲覧用アセット、`public.html`、`404.html` と更新したPublisherを配備する。アセットの同期には削除を付けず、古い記事が参照するアセットを残す。Publisherがテンプレートの配備前に起動して失敗した場合は、配備完了後に既存の再試行で処理されたことを確認する。
2. 代表記事1件を既存のPublication refreshまたは保存で再生成する。公開URLの生HTMLに `data-public-article="1"`、本文、記事固有のOGPが含まれ、参照されるCSS・JS・画像が取得できることを確認する。Publisherの失敗・再試行待ちが残っていないことも確認する。
3. 下記のdry-runで移行対象を確認する。旧HTMLと公開オブジェクトが欠落している記事が対象で、下書き・空記事・移行済み記事は含めない。`DSQL_HOST` は対象環境のLambda設定、`SITE_BUCKET` はTerraform outputと照合し、処理対象を取り違えない。実行権限は既存の本番runbookに従い、必要な権限のあるロールを使う。

   ```sh
   mise exec -- mairu exec --no-login --server asonas-aws "$AWS_ROLE" -- bin/refresh-published-pages --host "$DSQL_HOST" --site-bucket "$SITE_BUCKET" --html-first
   ```

4. 対象件数と経路を確認して同じコマンドに `--apply` を付け、公開更新を要求する。コマンドの終了は公開完了を意味しない。既存のPublisherが処理し、各記事のS3更新とCloudFront無効化が完了するまで待つ。途中で再実行しても移行済みの記事は再選択されない。dry-runの残件が0になること、Publisherの失敗キューが増えていないこと、対象URLが新しい内容であることを確認する。
5. 全公開記事の再生成と `404.html` の取得を確認した後に、CloudFrontの経路変更を含むTerraform変更を適用する。既存runbookどおりWebmentionの有効化フラグを維持し、fresh planを保存して全差分を確認し、そのplanだけをapplyする。apply後の再planで意図しない差分がないことを確認する。
6. 存在する記事は200、存在しない記事は404、`/editor/:id` は編集画面、検索とWebmention管理は従来の画面になることを確認する。記事名変更・非公開化の旧URLに本文が残らないことも確認する。

再生成の途中では新旧の公開HTMLが混在してよい。通常の保存でも新方式に更新される。再生成が失敗した記事がある状態で404切替を先に進めない。

ロールバックでは先にアプリケーションの配備を戻し、必要ならCloudFrontの経路変更を戻す。生成済み記事はコードのロールバックだけでは元に戻らないため、戻したPublisherで対象記事のPublication refreshを要求する。旧HTMLが参照するアセットを残しておく。

## 検証結果

### 記事表示の復元

2026-09-09、RubyKaigi記事の公開APIから取得したデータを固定し、旧閲覧画面と修正版をローカルで比較した。幅1568pxでカバー高さ350px、タイトル96px、本文外枠832pxが一致した。幅390pxと1568pxで横方向のはみ出しがなく、ユニバースの点をクリックして詳細カードを開けることを確認した。初期表示中の関連API要求は0回、ユニバースへ移動後は1回。関連APIの503時も本文を保持した。JS無効時も本文・編集リンクが残り、シマーは停止した。

本番反映には閲覧用アセットとPublisherの配備に加え、既存記事の再生成が必要。以下の移行時の性能数値は別構成の記録であり、復元後の性能値として扱わない。

### HTML配信への移行時の測定

2026-09-09、同一の合成記事を旧Publisherと新Publisherで生成し、ローカルHTTPサーバーとChromiumで比較した。本文・画像・2秒の動画・Speaker Deckリンクを含む。APIはローカルの固定レスポンスに600msの遅延を加えた。CDPで下り200,000 bytes/s、上り100,000 bytes/s、latency 100msを設定し、ブラウザキャッシュなし・ありを各3回測定した。

以下は各3回の中央値。localhostのTTFBは2〜7ms程度で、CDNやAWSの通信遅延を再現していない。CloudFrontのキャッシュヒット・ミスや本番のcold startを測定した値ではない。

| 条件 | 旧表示 | 新表示 |
| --- | ---: | ---: |
| キャッシュなし FCP | 1,340ms | 352ms |
| キャッシュなし LCP | 6,116ms | 352ms |
| キャッシュなし CLS | 0.220 | 0 |
| キャッシュあり FCP | 156ms | 164ms |
| キャッシュあり LCP | 804ms | 164ms |
| キャッシュあり CLS | 0.097 | 0 |
| キャッシュなし 初期JS転送量（resource timing） | 782,003 bytes | 3,088 bytes |
| 初期表示中の本文消失 | 3回とも発生 | 発生なし |
| 初期表示中の記事・認証API要求 | あり | なし |

キャッシュありのFCPは同程度。改善の中心は初回のJS転送量と、起動後の本文消失・API待ちをなくす点にある。LCP/CLSはこの代表記事と観測区間の値で、全記事の性能保証ではない。

ブラウザで確認した範囲:

- JS無効で本文・編集リンク・埋め込みの元リンクを表示し、シマーを残さない。
- 閲覧用JSを2秒遅延させても先に本文を読める。APIをすべて遮断した状態で、JS起動前後のスクロール位置が250pxに保たれ、API要求は0件だった。
- 幅390pxで横方向のはみ出しがなく、動きを減らす設定でシマーが停止する。
- 公開URLから既存エディタに遷移して本文が編集可能になる。認証・記事APIはこのブラウザ試験では固定レスポンスを使用。
- 動画の高さが再生前後とも414pxで、読み込み完了後に待機表示が終わる。
- 外部境界を固定したSpeaker Deckの成功時にiframeを表示し、503時は元リンクを残す。

MacのFirefoxとiPadのSafariによる実機確認、本番でのOGP・更新反映・経路とキャッシュの検証はデプロイ後の受け入れ条件として残る。
