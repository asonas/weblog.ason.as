# 公開記事のキャッシュ延長と公開時パージ

作成日: 2026-10-22。状態: Crit承認済み、ローカル実装・検証済み。本番配備・有効化・invalidation発行は未実施。

## 実装状況

1時間TTLとSWRは公開時パージと同じ有効化フラグで切り替える。フラグ未設定のランタイムは既存の3分TTLを維持する。本番有効化の承認を受け、Terraformの希望設定はtrueに変更した。新コードとスキーマのdeployment成功後にapplyする。公開の受け付け時に対象URLを永続化し、公開完了後に既存ジョブでパージする。改名は当該記事の旧・新URLまでとし、参照元はTTL更新に任せる。

管理画面には本サイトと確認済み配信設定の使用数、最終確認時刻、手動更新を実装する。削除済み・tenant配信を含む全アカウントの網羅を保証できないため、残枠は不明と表示する。下記の「残枠表示案」のうち、確認できない残数を表示しない方針を採用する。

公開URLの大文字を残し、ファイル名用変換は維持する。日本語・空白・文字としてのpercent encoding、公開前後の順序、再試行、認証境界をローカルで検証する。本番CloudFrontにおける旧URL表記の扱いとSWR更新中の競合は、導入時の実地確認として残る。[有効化手順](runbooks/public-delivery-cost.md#公開時のキャッシュ更新を有効にする)

検証結果: Ruby 520件・3,447 assertions、フロントエンド79件、Terraform12件が成功。Ruby/TypeScript型検査、RuboCop、Biome、Terraform validate、本番用フロントエンドbuildも成功。AWS APIはSDK境界のスタブで検証しており、実際のinvalidationによる課金や本番設定変更は発生させていない。

## 提案

CloudFrontが公開HTMLを1時間キャッシュします。その後5分以内にアクセスが来た場合、CloudFrontが期限切れを判断し、保持している古いHTMLを読者へ返すと同時に、オリジンから新しいHTMLを取得してキャッシュを更新します。期限になっただけで更新ジョブが走るわけではありません。記事を公開・再公開したときは、その記事のURLだけをパージします。編集用APIとMentioned by daysは現在のキャッシュなし取得を維持します。

直近14日間の本番公開履歴では、全記事を対象にしても月約147パス、末尾スラッシュ違いを含む2パス方式で月約293パスです。現在の更新頻度なら、アカウント共通の月1,000パス無料枠に収まる規模です。他distributionの消費分、将来の一括操作はこの見積もりに含みません。

目的は、閲覧時の待ち時間を減らしながら、公開した記事が1時間古いまま残ることを避けることです。以前のように関連する全ページへパージを広げません。

### 無料枠との比較

CloudFrontの無料枠はアカウント全体で月1,000パスです。複数パスを1リクエストにまとめてもパス数は減りません。同じURLへの別の公開に伴うパージも累積します。[AWSの課金単位](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/PayingForInvalidation.html)

本サイトのdistribution `E3BCWEKGAG5LSG` を読み取り確認したところ、最新のinvalidationは2026-09-21でした。確認時点でこのdistributionの10月実行はありません。他distributionの消費分は未確認なので、アカウントの残枠が1,000と断定はしません。

### 管理画面で無料枠の残数を表示する案

表示は可能です。ただし、このサイトの公開回数を1,000から引くだけでは、AWSアカウント全体の残枠にはなりません。管理画面では「今月の使用パス数」「無料枠の推定残数」「集計範囲」「最終確認時刻」を表示する案とします。リアルタイムの確定請求値ではありません。

アカウント全体を対象に、各distributionの `ListInvalidations` で当月のbatchを列挙し、`GetInvalidation` の `InvalidationBatch.Paths.Quantity` を合算できます。月境界はUTC、受付済みで進行中のbatchも含め、IDで重複排除します。リスト自体の `Quantity` はbatch数なので使いません。ワイルドカードも1指定として数えます。タグによる無効化を利用している場合も同じ無料枠を消費するため、集計対象から漏らさない設計が必要です。[ListInvalidations](https://docs.aws.amazon.com/cloudfront/latest/APIReference/API_ListInvalidations.html)、[GetInvalidation](https://docs.aws.amazon.com/cloudfront/latest/APIReference/API_GetInvalidation.html)

表示する残数は `max(0, 1000 − 当月の全対象の使用パス数)` です。別ツールからの実行や削除済みdistributionなど、全対象を確認できない場合は「本サイトの使用数」のみを表示し、アカウント残数は不明とします。取得エラーで使用数を0に戻したり、未確認分を未使用扱いにしたりしません。

ブラウザからAWSへ直接接続せず、認証済み管理APIが集計結果を返します。毎回全履歴を再取得せず、取得済みbatchの件数を保存して新規分を照合する案です。画面には更新時刻を出し、手動更新時にAWSとの差分を確認します。公開パージ処理には対象distributionの書き込み権限、残枠集計には必要範囲の読み取り権限を分け、アカウント全体へのパージ権限は与えません。表示のためのAWS読み取り・保存・API実行の費用はSWR機能の追加料金とは別です。

この表示は追加の設計案です。今回はドキュメントのみで、管理画面や集計処理は未実装です。無料枠に近づいた際の自動停止までを、この表示機能に暗黙に含めません。

表示例は「今月の使用数 293 / 1,000パス・推定残数707パス・アカウント全体・最終確認22:00」です。293は説明用の仮の実績で、上記の月間換算を実際の使用数として表示しません。本サイトしか取得できない場合は「本サイトの使用数293パス・アカウント全体の残数は未確認」とします。この表示案はレビュー対象のまま残しています。

## 現在の速度と変更後の動き

10月18〜20日UTCの取得済みCloudFrontログから、HTTP 200の公開HTML候補を集計しました。記事DBと照合した分類ではなく、記事とリンク関連ページを含みます。

| 状態 | 件数 | 応答開始時間の中央値 | p95 |
| --- | ---: | ---: | ---: |
| Miss | 5,324 | 1.430秒 | 2.106秒 |
| Hit | 35 | 0.005秒 | 0.029秒 |

ブラウザの描画完了時間ではありません。Hit件数も少なく、この数値を変更後の全アクセスに保証しません。

提案する公開HTMLのCache-Control:

```http
Cache-Control: public, max-age=0, s-maxage=3600, stale-while-revalidate=300, stale-if-error=86400
```

- 保存から1時間以内: キャッシュがあればそのまま返します。
- 1時間を過ぎて5分以内: 古いHTMLを返しながら、CloudFrontがオリジンから更新します。
- それ以降、またはキャッシュが存在しない場合: 通常のオリジン取得を待ちます。
- 公開・再公開後: パージが完了したURLは次のアクセスで新しい公開版を取得します。その最初のアクセスはMissになり得ます。

たとえば10:00にCloudFrontがHTMLを取得した場合、11:00までは通常のキャッシュです。11:02にアクセスが来ると、CloudFrontは古いHTMLをすぐ返し、裏でLambdaへ新しいHTMLを要求します。Lambda側は通常どおり公開済みデータからHTMLを返し、CloudFrontがそれを保存します。11:05まで待ってから更新するのではありません。11:00以降アクセスがなければ更新処理は走らず、最初のアクセスが11:06ならSWRの5分を過ぎているため通常の取得を待ちます。

期限の判定・古いHTMLの保持・バックグラウンド取得・キャッシュの置き換えはすべてCloudFrontの役割です。アプリに5分タイマーや別のHTML保存先は追加しません。5分は「期限切れのHTMLを返してよい猶予」であり、CloudFrontがその間必ず保持する保証ではありません。容量等の都合で既にキャッシュがなくなっていればMissになります。

SWRはアクセス時に動作し、全記事を定期巡回するジョブは追加しません。機能の追加料金はありませんが、更新時のAPI Gateway・Lambda・DSQL・S3の通常料金は残ります。現在も期限切れ時には取得・生成するため、SWRによる大きな費用増は想定せず、TTL延長で取得回数が減ることを期待します。削減額は未確定です。[SWRの仕様](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html#stale-while-revalidate)、[追加料金なしの案内](https://aws.amazon.com/about-aws/whats-new/2023/05/amazon-cloudfront-stale-while-revalidate-stale-if-error-cache-control-directives/)

現在のCloudFront `max_ttl=86580` は旧TTLに合わせた値です。既存の障害時猶予86400秒を維持するなら、1時間との合計を収める `90000` に合わせます。SWRの5分は通常時の提案値であり、障害時の `stale-if-error` は別の扱いです。

## パージ対象

| 操作・表示 | 方針 |
| --- | --- |
| 記事の初回公開・内容を変えた再公開 | 新しい公開版が有効になった後、当該routeだけ |
| 同じ内容の再送・同じ公開処理のリトライ | 新しいパージを増やさない |
| 下書きの自動保存・編集プレビュー | 対象外 |
| Mentioned by daysが表示される別の記事 | 対象外。APIをキャッシュなしで取得 |
| 未作成ページの「関連する記事」一覧 | TTLとSWRに任せる。通常公開から連鎖パージしない |
| RSS | 既存の1時間キャッシュを維持。記事公開時のパージ対象外 |
| トップ・検索・管理・API・404 | 現在のキャッシュ方針を維持 |
| 通常のデザインデプロイ、一括再生成・移行 | 自動パージ対象外。公開処理の共通経路から発火させない |

当該routeは、現在のコードが末尾スラッシュ付きでも本文を返すため、`/2026-10-21` と `/2026-10-21/` の2パスを基本案とします。`/2026-10-21*` のような前方一致は使いません。日本語routeは公開URLと同じエンコードに統一し、クエリはキャッシュキーに含まれないため列挙しません。任意の二重エンコードURL等まで自動列挙せず、特殊文字・非正規URLの扱いは実装時に検証します。[AWSのパス指定](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/invalidation-specifying-objects.html)

### 日本語・空白を含むURLの扱い

レビューで挙がった「「Where the tracks go next」を現地で見た。」は必須の検証例にします。提示されたURLからホストを除いたパスは次です。

```text
/%E3%80%8CWhere%20the%20tracks%20go%20next%E3%80%8D%E3%82%92%E7%8F%BE%E5%9C%B0%E3%81%A7%E8%A6%8B%E3%81%9F%E3%80%82
```

AWSは非ASCII文字と安全でない文字だけをURLエンコードし、それ以外を余分にエンコードしないよう指定しています。空白は `%20`、日本語はUTF-8のpercent encodingにし、完成済みのパスを再度エンコードして `%E3` を `%25E3` にしないことが必要です。

`W` はURLでそのまま使える文字です。RFC 3986のunreserved文字は英大小文字・数字・`-._~` であり、生成するURLではこれらをpercent encodingにしないのが標準的な方針です。`%57` は `W` と等価な表記ですが、積極的に生成する必要はありません。[RFC 3986 §2.3](https://www.rfc-editor.org/rfc/rfc3986#section-2.3)

現在の `WeblogAuthoring.encoded_route` は、ファイル名用の `encoded_page_name` を呼んでいるため `W` を `%57` にします。ファイル名側には、大文字小文字を区別しないファイルシステムで衝突を避ける意図があります。これはこのソフトウェア固有の事情が公開URLにも混ざっている状態です。公開URLに必要な一般的処理ではなく、ソフトウェア側を改善するのが妥当です。

今回の設計には、公開URLでは `Where` をそのまま `Where` と表現する方針を追加します。ファイル名用の変換を保ったままURL用の変換を分け、`encoded_route` が英大小文字をそのまま残すようにします。日本語・空白等は必要なエンコードを行います。既存の保存ファイル名を一斉に改名する変更は含めません。

生成される本文リンク・関連記事リンク・Mentioned by daysのリンク・リダイレクト先・フィードの閲覧URLを同じ方針に揃えます。既存の `%57here` リンクでも同じ記事へ到達できることを維持し、必要な場合は標準表記へのリダイレクトを検討します。文字として `%57` を含む記事名とは区別し、再帰的なdecodeや一律の小文字化はしません。フィードの永続IDなど、URLに似た識別子は表示用URLの変更に合わせて書き換えません。

実装時は、まず新しく生成する公開URLを `Where` 表記に揃えます。そのうえで、標準表記の `Where` と過去の `%57here` がCloudFront上でどう扱われるかを確認し、AWSの指定に従うパージで実際の公開URLの旧HTMLが除去されることを検証します。各表記の末尾スラッシュ有無、日本語・空白・文字としての `%` を含む名前も確認します。大文字小文字やUnicode正規化を無条件に変換して別記事のパスへ変えないようにします。ブラウザ独自の日本語の表示方法は制御対象外ですが、サイトが生成するURLの `Where` はエンコードしません。

これは採用前の確認条件です。本番URLは今回のWeb取得ツールでは読み取れず、公開応答・CloudFront内の同一視は未確認です。検証に伴う本番パージはまだ発行していません。1routeにつき2パスで対応できない場合は、対象表記・上限・費用試算を見直してから導入し、ワイルドカードで対象を広げて解決しません。

Mentioned by daysは `frontend/authoring/mentionedByDays.ts` が `/api/mentioned-by-days` を `cache: no-store` で取得し、API応答も `no-store`、CloudFrontの `/api/*` はキャッシュ無効です。掲載先HTMLをパージせず、次の読み込みで更新内容を取得できます。既に開いた画面が自動更新されるという意味ではありません。

### 改名と非公開化

改名は単なる旧URL・新URLの変更だけではありません。現在の `DraftRenames` は、参照元記事の本文も書き換えて同時に公開する場合があります。

改名した記事の旧・新routeをパージし、参照元記事の表示更新はTTLに任せる方針を採用します。旧URLのリダイレクトが利用できることを検証します。参照元も直ちに更新する仕様が必要になった場合は、実際に変更した改名メンバーだけを対象にし、件数を別途試算します。関連リンクを無制限にたどって対象を拡大しません。

非公開化・削除を行う経路がある場合も、オリジンで公開を止めた後に旧routeをパージする必要があります。パージは非同期で、閲覧者が既に保存した内容を回収するものではありません。非公開化の実際の経路とSWR更新中の競合を確認するまでは、即時削除を保証しません。

## 公開とパージの順序・再試行

1. 記事の公開版・必要な出力の準備を完了し、公開routeが新しい版を参照する状態にします。
2. その公開版に対応する固定の対象パスを永続化し、パージ処理を受け付けます。公開コミット後のプロセス停止でも処理を失わない仕組みにします。
3. `CallerReference` を公開版と固定パス集合から一意に決め、AWS呼び出しのタイムアウト後も同じ識別子・同じパスで再試行します。
4. 公開済みとキャッシュ更新中を区別します。パージ失敗で公開自体を巻き戻さず、既存のジョブ状態・再試行経路を利用します。実装前に既存ステージと共存できることを確認します。

公開前にパージすると、古い公開版が再びキャッシュされる可能性があります。公開と同時に走っている古いオリジン応答・SWR更新との競合も確認し、パージ完了後に旧版が残らないことを本番相当の確認項目にします。

入力パスはクライアントから任意に受け取らず、サーバー側の公開版から作ります。通常公開は最大2パス、改名の旧・新routeだけなら最大4パスに制限します。想定外の件数では自動送信せず、状態に理由を残してTTLへフォールバックします。全件取得やワイルドカードへ切り替える処理は置きません。

以前の事故は、記事の一括再生成が通常公開処理を通り、記事と未更新のWikiハブを繰り返しパージしたことが原因でした。今回も「1記事から呼ぶ」だけでは不十分で、実行契機・対象パス数・再試行を制限します。[当時の調査](postmortems/2026-09-11-aws-cloudfront-cost.md)

## 編集と確認

編集APIは `/api/authoring/drafts/{id}` の `private, no-store` を維持します。エディタ内プレビューは編集データから描画し、公開HTMLのキャッシュを使いません。新しい編集APIを作る必要はありません。

公開後に公開URLを開くと、パージ完了までは古い版を見る可能性があります。公開成功とキャッシュ更新完了を混同しない案内にします。公開済み版の即時確認用APIを新設するかは、既存プレビューと更新状態の案内で足りるかを見て判断し、この設計だけでは追加しません。

## 実装時の確認と導入順

1. 公開URLとファイル名の変換を分け、`Where` を維持したリンク生成と旧表記へのアクセスを確認します。続いてキャッシュ境界、通常公開・改名・一括処理の呼び出し経路を確認します。現在削除済みのCloudFront依存・IAM権限を戻す場合は、対象distributionに限定します。
2. 最小限の検証として、公開版切替後のパージ、同版再試行の重複防止、通常公開の2パス上限、一括処理と自動保存で未発火、編集APIのキャッシュ無効を確認します。
